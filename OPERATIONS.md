# Production operations — owner approval gates

## Edge deployment (not active)
Import the repository into Cloudflare Pages with build command `sh scripts/build-pages.sh`, output `dist`. Keep GitHub Pages serving existing links until the preview passes. Connect a domain you own; configure HTTPS and the WAF/DDoS policies available for your plan. Do not apply a blanket bot challenge to public search crawlers. Existing _headers only take effect on a compatible host. Run `python3 scripts/production_monitor.py --host YOUR_PREVIEW_HOST --strict-headers`; test actual login, recovery, MFA, certificate links, member permissions and images in staging. Preserve the old origin and URLs until cutover; update canonical, sitemap, hreflang, Auth allowlist and provider settings together. A WAF on the web host is not protection for direct Supabase API requests.

## Auth and access
Configure Turnstile or hCaptcha in its owner console and the matching Supabase Auth provider. Public site key only in security-config.js, never secret. Test login/signup/recovery together on staging before production activation. Supabase Free does not include native leaked-password protection; existing client-side screening remains enabled but cannot enforce Auth API calls. Do not buy or enable a paid service without owner consent. Use two dedicated, approved synthetic member accounts and a distinct admin account in an isolated test environment; confirm A cannot read or alter B's data, non-admin cannot manage the portal, and admin must complete MFA. Never use actual members as test targets.

## Backups and recovery
On an owner-controlled workstation, export a database backup using the supported Supabase backup procedure, and export Storage objects separately. Include the role/schema and Auth recovery requirements from the official backup/restore guidance. Keep plaintext exports outside this repository on encrypted local storage; do not export data in CI. Verify the backup recipient's OpenPGP fingerprint independently. Encrypt each local export with `bash scripts/backup-encrypt.sh INPUT_FILE OUTPUT.gpg RECIPIENT_FINGERPRINT`. Record SHA-256 and backup date in a private inventory. Keep the private recovery key separately under owner control. Use GPG on a trusted workstation to verify decryption and integrity; restore to a distinct isolated project, never overwrite production for a test. Verify data integrity, RLS, Auth and storage references; document RPO/RTO and cleanup. The synthetic encryption test does not prove a real data backup or restore.

## Search visibility

Register a custom domain only after owner selection and cost approval.

## V69 email-code password recovery — required hosted configuration
In Supabase Dashboard > Authentication > Email Templates > Reset password, set the subject to `آل برهم | رمز استعادة كلمة المرور` and paste `supabase/templates/recovery.html` into the template body. The template uses {{ .Token }} and a plain portal link, not a token-bearing link. Keep existing SMTP and redirect allowlist; verify actual delivery with a dedicated test account. OTP length and expiry are determined by Supabase (UI accepts 6–8 digits). Set a short expiry, e.g. 10 minutes, and appropriate Auth rate limits in the dashboard after checking effects on other email flows. Do not paste OTPs, passwords or provider secrets into chat or Git. Browser and unit tests use fake accounts/mocked auth; they do not prove email delivery. Existing password-reset links remain supported. The account password-change button now routes through email recovery; provider-side enforcement of all password changes is separate from the website UI.

V70: signed-in recovery uses a server-verified confirmed email, locked in the UI; guest recovery uses Supabase's existing-account recovery endpoint without creating accounts or exposing an email directory. The proof expires in the UI after ten minutes following successful verification; actual OTP expiry and throttling are provider settings. The portal does not enforce these UI limits on direct Auth API calls. For a strict requirement to restrict mail to approved membership records rather than registered Auth accounts, an Auth-provider-side policy/hook is required; do not substitute an exposed email lookup. Test live delivery only with an owner-approved test inbox.


## V79 edge and credential activation checklist
- Cloudflare Pages: import this repository, use main / sh scripts/build-pages.sh / dist. Keep old GitHub Pages origin live. A pages.dev preview can be tested at no additional hosting cost; custom WAF rules for a domain require control of that domain and appropriate Cloudflare configuration. Do not claim the github.io hostname is behind a newly configured WAF.
- Turnstile: https://dash.cloudflare.com/ → Turnstile → create widget for the intended hostname. In Supabase Authentication attack protection select Turnstile and enter the secret privately; set only the public widget key in security-config.js. Coordinate both changes, test signup, login and recovery with a dedicated test account, and roll back both settings if necessary. Never use test keys in production.
- WebAuthn: choose the final stable RP ID first (changing it invalidates passkeys); enable in Supabase Authentication → Passkeys with the exact HTTPS origin(s). Confirm SDK and browser support, register and sign in with a test account, test recovery, then set passkeysEnabled true. Do not bypass the administrative AAL2 requirement. Feature remains experimental in the SDK documentation.
- Secret scans: raw history and public build are always scanned. The separate historical classification is restricted to the exact existing publishable client key, generic-api-key rule and portal.js path. Other findings fail. No secret/service-role key may be exempted. Review logs before closing the historical finding.

## V80 performance and resilience acceptance gates

- Preserve existing GitHub Pages deployment and service worker no-store behavior. Only three public icon assets get a short browser TTL on compatible edge hosts; never cache authenticated APIs, signed storage links, recovery or personalized data at the edge. Cloudflare Pages default caching and automatic compression are preferred; do not add Cache Everything.
- Before migration, use the Cloudflare Pages Git integration with `sh scripts/build-pages.sh` and output `dist`. Keep canonical and Auth redirects unchanged until a verified custom-domain cutover. A pages.dev host is useful for staging, not evidence of a WAF on github.io.
- Probe transfer encoding, ETag revalidation and Cloudflare headers with `python3 scripts/edge_probe.py --host PREVIEW_HOST --require-cloudflare`. Gzip is decoded and compared to the identity body; Brotli is reported from its response header only. A Cloudflare header is not proof of a configured WAF. Use dashboard security events to verify available DDoS/WAF rules without launching attack traffic.
- Public health monitor is scheduled hourly after merge; GitHub schedule is best-effort, not a guaranteed SLA. Configure an independent uptime monitor (e.g. 5-minute HTTPS checks and a private alert channel) separately.
- The owner-approved staging baseline uses `python3 scripts/staging_load.py --host PREVIEW_HASH.PROJECT.pages.dev --owner-approved`. It is bounded to 100 static requests, 5 workers, stops after errors, and refuses the production hostname. It is not a full user-capacity or Auth load test. Larger end-to-end tests require an isolated Supabase staging project, synthetic users, provider rate/budget review and a separately approved test plan.
- Run `database/operational_capacity.sql` in the private SQL editor for current aggregate counts. For continuous monitoring use Supabase Observability and Usage, compare with actual plan quotas, and set private alerts at 70/85/95% where supported. Do not publish usage metrics, credentials or private records in public CI logs. Do not change Supavisor pool size without evidence of pressure; browser clients use HTTPS APIs, not database connection strings.
- For SMTP, use a verified sending domain/provider and configure SPF/DKIM/DMARC. Keep SMTP and Turnstile secrets in provider settings only. Verify recovery delivery and OTP with an approved synthetic mailbox; do not send messages to real members as a test.

## V81 release integrity and low-risk hardening
- The build rejects unknown files and symlinks in generated dist, including leftovers from prior builds. If the build refuses an old output directory, review it privately and create a fresh output directory; never copy arbitrary repository files into the site. The Jekyll exclusion list separately excludes operations documentation. The Git repository itself is public; exclusion is not confidentiality.
- Production monitoring compares both the live homepage release references and SHA-256 of the actual CSS/JS response bytes against the expected checkout after a successful Pages workflow or on a scheduled/explicit check. A successful merge alone is not proof of deployment. Public probe logs contain only status and aggregate timing/size, not response contents.
- The browser workflow includes the real home route in Lighthouse lab measurements and runs for JavaScript/HTML-only PRs. Total blocking time is a lab metric, not real-user INP. Field metrics and large concurrent-user testing require representative traffic and isolated staging.
- Do not expose raw provider errors to visitors; preserve validation messages and generic recovery guidance. No production database or provider settings are changed in this release.

## V82 network, quality and privacy checks
- Runtime preferences: explicit data-saver button with automatic network hints where supported; image signed URLs are requested only on user action in low-data mode. No private API caching, no queued offline mutations. Offline fallback is a static explanation, not offline access to membership records. Local diagnostics report only LCP, CLS, aggregate browser error/rejection counts for the current visit. No telemetry transmission, local metric persistence, URLs, messages, stacks or identifiers. This is not a central RUM/Sentry deployment.
- Admin editor uses a same-origin dynamic import after server authorization. The public route must not eagerly download it. RLS remains authoritative. Frontend split does not protect code itself.
- Cross-browser checks run Chromium, Firefox, WebKit with mocked/unreachable backend. Lighthouse regression budgets are provisional (50 performance, 95 accessibility, CLS <= 0.25); the target remains 95 performance, LCP <= 2500ms, CLS <= 0.1. The workflow is not an enforced main-branch ruleset. Repo main protection was reported false; configure required checks in GitHub Settings > Rules > Rulesets with owner approval. Do not disable existing checks.
- Protocol probe independently verifies decoded Brotli against identity when negotiated; HTTP/3 requires actual negotiation, Alt-Svc is advertising only. GitHub Pages cannot be configured here for server compression or QUIC. No changes to DNS or hosting.
- Native breached-password protection requires Supabase Pro; no plan change. Passkeys remain experimental and disabled pending stable RP ID, provider activation and dedicated account recovery tests. See https://supabase.com/docs/guides/auth/password-security and https://supabase.com/docs/guides/auth/passkeys.
- Sentry requires an owner-controlled project and privacy-reviewed DSN/transport; do not capture URLs, tokens, user input, session replay or private records. Resource thresholds are evaluated by the read-only SQL diagnostic; central alert delivery still requires private provider settings. Full load tests require isolated staging and approved quotas; loopback static baseline does not prove production concurrency.

## V83 critical rendering
Home navigation and mobile dock render as static HTML. The home uses stable Arabic-capable system fonts; decorative web fonts are loaded on other routes only when data-saver is off. Existing SDK integrity, authorization guards and route semantics remain unchanged. News images are requested near the viewport; no private cache. Reduced animation, reserved slots and local-only diagnostics support CWV optimization. The initial visual style of typography may differ by device. The Lighthouse test retains its previous hard thresholds and reports remaining performance opportunities; a single lab run is not field CWV evidence. No provider, database or paid-plan changes.

V83 visual refinement: use 82% opacity for card/hero backgrounds and 86% for navigation chrome, not element opacity. Keep existing emerald/gold foreground palette, light ivory surfaces, dimensions and print scope. Keep the header and dock blur-free for rendering performance. Reduced-transparency preference retains solid surfaces. These are design parameters, not measured contrast guarantees; retain browser palette and accessibility regression checks.
