# Privacy and resilience upgrade — staged, not production activation

## Owner approval and implementation gates
- Review Arabic privacy wording, identify a responsible contact, applicable legal basis, retention schedule, deletion and incident-response process. Adult self-attestation is UI only; review age/guardian consent through a private, server-side application workflow without collecting unnecessary birth dates. Historical public genealogy includes names and relationships without age verification; have an authorized editor review living/minor records and redact only after approval. Do not treat noindex as access control.
- Apply database/member_mfa_session_gate.sql in a separate staging Supabase project. Run database/security_isolation_regression.sql. With two dedicated test member accounts, verify own records, denial of other-account reads/writes/deletes, storage object access, all security-definer RPCs and AAL1/AAL2 sessions. Verify account recovery, existing admin login and public certificate verification. Do not deploy if any fail. Check policies and privileges separately for anonymous access.
- Existing security dashboard now distinguishes blocked attachments and operational/recovery alerts. These are aggregate indicators, not confirmed attacks or a managed SIEM. For production SIEM use an owner-approved private log destination with minimal data, TLS, retention, monitoring of log delivery and tested alert routing. Do not send tokens, request bodies, children's data or private files.
- Deploy scripts/private-av-scanner.py on a privately managed hardened server with a supported ClamAV release, freshclam signature updates, clamd socket, unprivileged account, encrypted transport via TLS reverse proxy, strict request size and rate limits, secret management and restricted network access. Configure PRIVATE_AV_SCAN_URL and PRIVATE_AV_SCAN_TOKEN privately in Supabase; never commit secrets. Test with synthetic clean and industry-standard harmless antivirus test files in staging. Outage, timeout or mismatched hashes must never release a file. Review attachment object immutability and scanner freshness. No private documents may be sent to public malware scanners.
- Immutable backups: owner chooses lawful retention and budget, creates separate S3 bucket with versioning/Object Lock and least-privilege role, blocks public access and confirms account ownership. Export DB and storage separately on a trusted workstation, encrypt with existing backup-encrypt.sh, then use backup-object-lock.sh to upload each encrypted archive with explicit COMPLIANCE retention and verify SHA-256 and version retention. Retention cannot be shortened; choose dates carefully, with privacy deletion obligations in mind. Record version IDs/checksums privately; test decryption and full restore in an isolated project. No actual backups are created by this PR.
- PQC: inventory TLS at browser/edge and Supabase, authentication keys, certificate verification and OpenPGP backups; document algorithms and owners. NIST FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA. Use supported provider implementations and crypto-agile migration, not homegrown algorithms. Run pqc-probe.sh on OpenSSL 3.5+ with synthetic data to assess local algorithm support. Do not alter certificate signatures or existing backup encryption until compatibility, recovery and provider support are validated. No production PQC claim.
