**الهوية المقترحة:** إدارة بوابة آل برهم · `albarham.inc@hotmail.com` · [الموقع الرسمي](https://barham-ps.github.io/)

**حالة الإصدار (26 نوفمبر 2026):** حساب Make مؤكد، اتصال Microsoft 365 Email (Outlook) قائم بصلاحيات `Mail.Send` و`User.Read` و`offline_access` فقط. سيناريو `Al Barham – Hotmail delivery test` محفوظ وغير نشط؛ لا يرسل إلى الأعضاء. **نجح اختبار إرسال فعلي واحد من Make إلى البريد الرسمي نفسه** يوم 26 نوفمبر 2026 الساعة 22:22 بتوقيت فلسطين: وحدة Outlook نفذت عملية واحدة واستهلكت رصيدًا واحدًا، ظهرت الرسالة بعنوان «اختبار الإرسال الآلي | بوابة آل برهم» في المرسلة عند 22:22:43 ثم الوارد عند 22:22:47. أول تشغيل عام سجل صفر عمليات لأن الوحدة لم تكن متصلة بمسار؛ تم تشغيل وحدة الإرسال مباشرة بعد التحقق من عدم إرسال شيء في المحاولة الأولى. تم اختبار القوالب والطابور والواجهة المحاكية محليًا، واختبار SQL ضمن معاملة انتهت بـ `ROLLBACK`. **هذا يثبت تسليمًا تجريبيًا من Hotmail، ولا يثبت تشغيل منظومة الإنتاج.** لا تُغيّر SMTP الحالي ولا تفعّل Auth Hook حتى نجاح كل الاختبارات الفعلية التالية.

## 1. القوالب الجاهزة

- مصدر واحد: `supabase/functions/_shared/mail-catalog.mjs`، يتضمن عنوان كل رسالة والنص والتوجيه الآمن والمرسل المقصود.
- `supabase/templates/catalog.json` فهرس الآلات والإدارة: 13 قالب مصادقة وأمان، 59 قالبًا للأحداث والمعاملات.
- `supabase/templates/*.html`: 13 ملف HTML جاهزًا لحقول Supabase Auth، متطابق مع تصميم البوابة (أخضر زمردي، ذهبي، RTL، نص واضح على الهاتف، روابط رسمية، بدون صور متعقبة أو JavaScript).
- بقية الرسائل تُولّد عبر `renderEvent` من معرّف حالة ثابت، لا من مدخلات المستخدم. لا تتضمن نص الشكوى أو رد الإدارة أو اسم الشخص أو رقم العضوية أو رقم الهاتف أو المرفقات. مرجع الطلب UUID فقط داخل الرسالة، لا في العنوان.
- الرسائل التلقائية تشرح أن التسجيل لا يعني قبول العضوية. يظل اعتماد العضوية والشهادة وظهور الوثائق محكومًا بإجراءات وقواعد الموقع القائمة.

## 2. بنية الإرسال الآمن للأحداث الإدارية

```text
حدث موثوق من جدول محمي → طابور خاص (معرّف/حالة فقط)
  → عامل Supabase مُصادق عليه → Webhook Make (معرّف عشوائي فقط)
  → طلب HTTPS مصادق لجلب عنوان المستلم والقالب من Edge Function
  → Microsoft 365 Email / Send an Email (Hotmail)
  → تأكيد قبول Outlook إلى Edge Function
```

- `database/mail_outbox.sql` يربط تحديثات حالات العضويات، طلبات الأعضاء، المراسلات، الشهادات والإشعارات. الطابور خاص، RLS مفعّل، ولا صلاحية `anon` أو `authenticated` لدواله. عند تثبيته يظل جمع الأحداث **متوقفًا** (`enabled=false`). لا ترسل بيانات المستخدمين أثناء التثبيت. لا يضيف أحداثًا بأثر رجعي.
- `supabase/functions/mail-outbox/index.ts` نقطة خادمية فقط. لا يتلقى مستلمًا أو نصًا أو قالبًا من المتصفح أو من عنوان خارجي: يطلب معرّفًا موجودًا مسبقًا في الطابور؛ المطالبة ذرية ومرة واحدة. استخدام سرين منفصلين للإرسال والجلب، مفاتيح سرية في Vault/Edge Secrets، وعناوين ثابتة محققة. يعرض القالب التفاصيل داخل البوابة المحمية ولا يرسل البيانات الحساسة في البريد.
- مراحل الطابور `queued → dispatched → sending → sent/failed/uncertain`. قبول Webhook ليس إثبات تسليم. لا تعِد إرسال حالة uncertain تلقائيًا؛ راجع حالة العملية لدى Outlook كي لا تتكرر الرسائل. الحد الافتراضي 120 رسالة أحداث شهريًا مع احتياطي لحصة Make المجانية، ويُراجع بعد حساب عدد العمليات الفعلي. تنتهي مهلة المطالبة بعد 10 دقائق، وتنتهي الأحداث القديمة غير المرسلة بعد 7 أيام. حذف سجلات الطابور المنتهية بعد 32 يومًا (دورة تشغيل العامل).

### إعداد سيناريو Make الإنتاجي (لا يُفعّل قبل الاختبار)

1. إنشاء سيناريو مستقل، اسم `Al Barham – Secure event mail`، Webhooks → Custom webhook محمي بمفتاح API خاص (`x-make-apikey`). لا تقبل عنوان مستلم أو نصًا داخل طلب Webhook؛ بنية الطلب الوحيدة `{"job_id":"UUID"}`.
2. تفعيل **Data is confidential** في Scenario settings قبل أي بيانات مستلم. طلب Webhook نفسه يُصفّ في Make حتى مع تفعيل السرية، ولذلك يحتوي فقط على معرّف عشوائي. لا تحفظ بيانات HTTP المرسلة أو المستلمة يدويًا في ملاحظات التنفيذ.
3. HTTP → Make a request: `POST https://vfxxghfmkmgdqrczeowx.supabase.co/functions/v1/mail-outbox?action=claim`، نوع JSON، Body `{"job_id": <mapped webhook job_id>}`، وتخزين رمز الجلب في Make connection/credential. Header Authorization: Bearer [MAIL_MAKE_PULL_SECRET]. لا يُرسل Supabase service key إلى Make.
4. ربط Microsoft 365 Email (Outlook) → Send an Email بالاتصال `Al Barham – Hotmail (Send)`؛ From الحساب المعتمد، To/Subject/Body من حقول نتيجة الخطوة السابقة `to`, `subject`, `html` فقط. لا تضف مستلمين افتراضيين أو CC/BCC. Content type HTML. لا تتبع الرابط إذا كان التنفيذ فاشلًا.
5. HTTP → POST إلى نفس الدالة `?action=finish` بالسر نفسه وJSON `{"job_id": <mapped id>, "outcome":"sent"}` فقط إذا قبل Outlook الطلب بنجاح. اختبار وحدة Send an Email أعاد نجاحًا دون حزمة مخرجات، لذلك يجب اختبار استمرار المسار ووصول ACK فعليًا قبل التفعيل. إذا توقّف المسار بعد الوحدة، استعمل إجراء Graph API الموثق الذي يعيد حالة HTTP 202 أو مسار إنهاء موثّق من Make، ولا تسجل `sent` دون دليل القبول. في مسار فشل مؤكد استخدم `failed`، وفي حالة مهلة أو نتيجة غير معلومة `uncertain`. إذا فشل ACK تبقى المهمة غير مؤكدة ولا تكرر إرسالها.
6. اختبر أولًا بعنوان الإدارة وببيانات اختبار اصطناعية. تأكد من From، RTL، زر البوابة، وصول البريد الفعلي، عدم ظهور محتوى الشكوى أو معلومات حساب في سجل Webhook، ومنع إعادة نفس job ID. راجع رسوم Make، ولا تستخدم خطة مدفوعة بدون موافقة المالك.
7. عند نجاح الاختبار فقط: ثبّت SQL في مشروع Supabase، افحص المستشار الأمني والصلاحيات، انشر Edge Function مع `verify_jwt=false` **لأنها تتحقق بنفسها من سر مستقل وعالي العشوائية**. تعيين أربعة أسرار: `MAIL_DISPATCH_SECRET`, `MAIL_MAKE_PULL_SECRET`, `MAIL_MAKE_WEBHOOK_KEY`, `MAIL_MAKE_WEBHOOK_URL`. لا تحفظ أي سر في Git أو frontend أو رسائل المحادثة.
8. اضبط Supabase Cron لإرسال `POST ?action=dispatch` مع سر `MAIL_DISPATCH_SECRET` من Vault؛ لا تحتاج Make إلى polling دوري. اختبر مع الطابور غير نشط أولًا، ثم تفعيل الإعداد `enabled=true` بعد نجاح اختبار end-to-end. لا تمرر جميع سجلات الأعضاء أو طلباتهم إلى Make.
9. إيقاف طارئ: إيقاف جمع الأحداث `enabled=false`، وإيقاف الجدولة وسيناريو Make. لا تتغير حالة العضوية أو نجاح الطلب بسبب نتيجة البريد؛ يبقى السجل داخل البوابة.

## 3. الاستعادة والتسجيل عبر Hotmail — بوابة تفعيل مستقلة

لا يُفعّل Send Email Hook الحالي قبل اختبار حقيقي آمن لكل نوع من أنواع Auth. عند تفعيله يستبدل SMTP لكل رسائل المصادقة، وهذا قد يوقف التسجيل والاستعادة إن كان خط الإرسال غير جاهز. تصميم الارتباط: تحقق من توقيع Standard Webhooks داخل Edge Function؛ استخدم قالبًا مطابقًا لنوع حدث Auth؛ أرسل فقط معرف مهمة إلى Webhook؛ احفظ محتوى الرسالة/رمز الاستعادة مؤقتًا مشفّرًا بمفتاح خادمي وصلاحية قصيرة، ثم اسمح لـMake بجلبه مرة واحدة من قناة HTTPS موثقة مع التحقق من قبول Outlook قبل رد نجاح على Auth Hook. لا تُسجّل رمز OTP أو الرابط في logs ولا ترسلها في جسم Webhook المخزّن.

هذا المسار الحساس **لم يكتمل ولم يُنشر** في هذا الإصدار. اختبر `signup`, `recovery`, `invite`, `magiclink`, `reauthentication`, `email_change` (بريدان إذا تطلب إعداد الأمان ذلك) والإشعارات المفعّلة. تحقق من مهلة تنفيذ Auth Hook الفعلية، ومن سلوك التأخير والرفض (لا نجاح وهمي)، ومن أن الرمز يظل صالحًا للاستخدام مرة واحدة فقط. إذا لم تلائم السرعة أو الحصة أو ضوابط الخصوصية Free Make، استخدم مزود إرسال معاملاتي مع دعم موثق للمصادقة دون تعطيل الخدمة القائمة. قوالب المصادقة الـ13 موجودة في المستودع، ولم يُغيّر SMTP أو Auth Hook في الإنتاج.

## 4. أدلة الاختبار المحلية

```sh
node scripts/build-email-templates.mjs --check
node --test tests/mail-templates.test.cjs tests/mail-outbox.test.cjs
```

اختبارات التوليد حتمية. تفحص قالب OTP و13 قالب مصادقة و59 قالب حدث، العناوين والاتجاه والروابط، منع مدخلات HTML، التحقق من مفاتيح القوالب، الحماية من المطالبة غير المصرح بها، معرفات UUID فقط، ورفض إعادة المطالبة. جرى اختبار SQL مع قاعدة المشروع ضمن معاملة انتهت بالتراجع؛ تأكد غياب الجدول والدوال بعدها. `mail_outbox_regression.sql` يتطلب قاعدة معزولة أو معاملة تراجع مع SQL المذكور، وليس أمر تشغيل الإنتاج. لا توجد مفاتيح إنتاج أو بيانات شخصية في هذا الكود.
